# Part 6 — Plan → Tasks → Implement

> **이 문서의 위치**
> 7부작 중 6부(실행 순서상 Part 3 게이트 통과 직후, Part 4 검증 직전). 검증된 설계를 **의존성 순서의 태스크로 쪼개 단계적으로 구현**하는 단계를 정의한다. 헤비유저 워크플로(spec-kit `/plan → /tasks → /implement`)의 핵심이자, 초기 5부작에서 빠져 있던 다리.
> 본문은 도메인 중립. 이번 SRCNN 사례는 말미 **[사례 부록]**.

---

## 1. 왜 이 단계가 따로 필요한가

설계(Part 1·2)가 "무엇을·왜"라면, 이 단계는 "어떤 순서로". 설계가 완벽해도 구현을 한 덩어리로 시도하면 두 가지가 터진다:

1. **컨텍스트 폭발** — 큰 구현을 한 세션에 밀어넣으면 60% 룰을 금세 넘긴다(Part 0 §3).
2. **검증 불가** — 한꺼번에 만들면 어디서 틀렸는지 분리가 안 된다. 작은 태스크 단위여야 태스크마다 검증(Part 4)을 붙일 수 있다.

그래서 **Plan(전략) → Tasks(의존성 정렬된 작은 단위) → Implement(태스크별 구현+검증)** 로 나눈다.

---

## 2. Plan — 구현 전략

설계 문서(architecture, module_contracts)를 입력으로, **구현 순서와 단계 분할**을 담은 `plan.md`를 만든다.

`plan.md`에 들어갈 것:
- **구현 단계(phase)** 와 각 단계의 목표.
- **단계 의존성 그래프** — 무엇이 무엇보다 먼저 와야 하는가(예: 메모리/인터페이스 먼저, 데이터패스 나중, 통합 마지막).
- **파일 생성/수정 표** — 각 단계가 건드릴 파일을 미리 명시(spec-kit의 file-creation table).
- **각 단계의 검증 기준** — 이 단계가 끝났다고 말할 수 있는 조건(어떤 golden과 대조하는가).

> **운용 팁 — 주석(annotation) 사이클**: Claude가 `plan.md` 초안을 쓰게 한 뒤, 사람이 에디터에서 열어 **잘못된 판단이나 모호한 곳에 인라인 메모**를 단다("여기는 X 방식으로", "이 가정 확인 필요"). 그 주석 단 파일을 다시 읽혀 플랜을 고친다. 헤비유저들이 가장 효과를 보는 플래닝 방식이다 — 사람이 통제권을 쥔 채 모호성만 빠르게 붕괴시킨다.

---

## 3. Tasks — 의존성 정렬된 실행 단위

`plan.md`를 입력으로, 실제로 실행 가능한 태스크 목록 `tasks.md`를 만든다. 좋은 태스크의 속성(spec-kit 기준):

- **의존성 정렬** — 모델/인터페이스 → 서비스/로직 → 통합 순. 앞 태스크 출력이 뒤 태스크 입력.
- **병렬 표시** — 서로 독립인 태스크는 `[P]`로 표시해 병렬 가능함을 명시.
- **정확한 파일 경로** — 각 태스크가 어느 파일을 만들/고칠지 명시.
- **테스트/검증 우선** — 가능하면 검증 기준(또는 테스트)을 구현보다 먼저 적는다(TDD 구조).
- **충분히 작게** — 한 태스크는 한 세션의 60% 안에서 구현+검증이 끝나는 크기.

태스크 양식 예:
```markdown
## T-007 [P] uram_bank write 라우팅 구현
- **deps**: T-003(URAM 인스턴스), T-005(module_contract 확정)
- **files**: rtl/uram_bank.v
- **done-when**: L1 4채널 동시 write가 같은 주소로 나가고,
                 layer_cnt별 we 라우팅이 contract와 일치 (단위 검증 통과)
- **verify**: Part 4 — golden_L1과 4채널 write 주소 시퀀스 대조
```

---

## 4. Analyze — 구현 전 일관성 게이트

구현(`/implement`)에 들어가기 **전에**, spec/plan/tasks가 서로, 그리고 constitution(CLAUDE.md hard rules)과 일관되는지 한 번 검사한다(spec-kit `/analyze`에 해당). 읽기 전용 점검이며, 발견된 불일치를 먼저 고친 뒤 구현한다.

점검 항목:
- 모든 태스크가 어떤 설계 결정(DEC)에 근거하는가? 근거 없는 태스크 = 누락된 결정.
- module_contract와 태스크의 인터페이스가 일치하는가?
- 의존성 순환은 없는가?
- 각 태스크에 검증 기준이 있는가?

> 이 게이트가 잡는 게 바로 "구현 후에야 드러나는 구조적 모순"이다. 구현 전에 잡으면 플랜·태스크를 아직 싸게 고칠 수 있다.

---

## 5. Implement — 태스크별 구현 + 즉시 검증

태스크를 **의존성 순서로 하나씩** 구현한다. 각 태스크는:

1. 구현(코드 작성/수정).
2. `done-when` 기준으로 **즉시 검증**(Part 4). 통과 못 하면 다음 태스크로 안 넘어간다.
3. 커밋(태스크 1개 = 커밋 1개, 추적성 확보).
4. `logs/`에 진행 append.

**핵심 규율**:
- **회귀 먼저.** 기존 동작을 건드리는 태스크는 "기존과 동일"을 먼저 증명하고 새 기능을 얹는다(Part 4 §7).
- **단계적 확장.** 단일 단위 → golden 대조 통과 → 확장. end-to-end는 마지막.
- **신선한 세션으로 실행.** spec이 완성되면 새 세션에서 실행하라(헤비유저 권장). 설계 대화의 잡음 없이 깨끗한 컨텍스트로 구현 시작.
- **diff 리뷰를 격리 컨텍스트로.** 태스크 완료를 "done"으로 치기 전에, subagent(또는 새 컨텍스트)로 diff를 검토해 빠진 곳을 보고받는다.

## 6. Claude Code 구성 (최소)

Part 0 §3.4·Part 3 §5.2의 안티패턴 경계를 따른다 — harness의 plan mode가 2·3단계를 상당 부분 대신하므로, **커스텀 커맨드는 필수일 때만**.

- 가능하면 harness의 **plan mode**를 Plan 단계에 그대로 쓴다(커스텀 플래닝 커맨드 불필요).
- `tasks.md`는 파일로 유지하고, 구현 세션 시작 시 읽힌다.
- 정말 반복되는 점검(analyze)만 슬래시 커맨드/스킬로 둘 수 있다. 그 외는 자연어.

## [사례 부록] SRCNN 프로젝트에 이 단계가 있었다면

> 재사용 시 교체.

이번 프로젝트에서 **정확히 이 단계가 비어 있어서 막혔다.** 단일 채널 경로(FSM/line_buffer/pe_group/타이밍)는 확정·검증됐지만, `top.v`의 **병렬 인스턴스화**(weight_dispatch, channel_accumulator, URAM 6뱅크, line_buffer 4병렬, L1 4채널 동시 write)가 미완으로 남았다. 이건 설계가 없어서가 아니라 — 설계는 `verification_notes.md`에 있었다 — **구현을 의존성 순서의 작은 태스크로 쪼개 단계적으로 짓는 절차가 없어서**다.

이 단계가 있었다면 `tasks.md`는 대략 이렇게 나왔을 것이다(의존성 정렬):

```markdown
## Phase A — 메모리/인터페이스 (선행)
T-01    URAM 6뱅크 인스턴스 (uram_L1×4, uram_L2×2)
T-02    FIFO 6인스턴스 (64→16), wr_en ← uram rd_valid 연결   # 7.1/7.2 PENDING 해결
T-03 [P] weight_dispatch 통합 (L1 dispatch 경로)

## Phase B — 데이터패스 (T-01~03 후)
T-04    line_buffer 4병렬 인스턴스
T-05    pe_group 4병렬 + channel_accumulator(Σ4) 연결
T-06    uram_bank write/read 라우팅 결선

## Phase C — 통합/루프 (T-04~06 후)
T-07    out_ch 루프 + 레이어 전환 mux (L1병렬4 / L2·L3누적1)
T-08    L3 + 최종 출력 경로

## Phase D — 검증 (각 태스크 done-when으로 분산, 여기서 종합)
T-09    L1 4채널 → golden_L1 대조
T-10    L2 한 out_ch → golden_L2 / 그 다음 out_ch
T-11    L3 → golden_out / end-to-end
```

그리고 **Analyze 게이트**가 구현 전에 잡았을 것들:
- T-02의 "wr_en ← rd_valid"가 prefetch ADR과 일치하는가 → 일치 확인 후 진행.
- T-05의 channel_accumulator 인터페이스가 module_contract(21bit partial × MAX_CH)와 맞는가.
- ReLU PENDING이 T-05/T-08 어디에 들어갈지 결정됐는가 → 미결이면 "conv-only로 확정" DEC를 받고 통과.

요컨대 이 프로젝트의 마지막 미완(top 병렬화)은 **Part 6을 적용하면 곧바로 실행 가능한 태스크 목록으로 떨어진다.** 다음 세션에서 이 `tasks.md`를 만들고 Phase A부터 태스크별로 구현+검증하면 된다.
