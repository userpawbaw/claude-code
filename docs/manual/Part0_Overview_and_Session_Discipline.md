# Part 0 — 개요 & 세션 운용 규율

> **이 문서의 위치**
> 7부작의 진입점. 나머지 6개 문서가 무엇이고 어떻게 맞물리는지, 그리고 모든 단계에 공통으로 적용되는 **컨텍스트·세션 규율**을 정의한다. Claude Code 세션을 시작하기 전에 이 문서를 먼저 읽는다.

---

## 1. 이 매뉴얼은 무엇인가

AI 코딩 에이전트(Claude Code)로 **설계→문서화→구현→검증→학습**의 전 주기를 규율 있게 돌리기 위한 운용 매뉴얼이다. "코드를 더 빨리 뱉게" 하는 게 아니라, **틀린 코드를 덜 만들고, 틀렸을 때 빨리 좁히고, 끊겨도 복원하고, 다음 프로젝트가 더 나아지게** 하는 구조를 만든다.

대원칙 하나로 요약하면: **실행 전에 모호성을 붕괴시키고, 실행 후에 증거로 검증한다.**

근거(헤비유저 공통 통찰): 한 결정의 정답률이 80%여도 기능 하나에 결정이 20개면 전부 맞을 확률은 약 1%다. 플래닝과 검증은 이 곱셈을 끊는다. Anthropic 내부 측정에서도 무가이드 시도의 성공률은 약 1/3이었다 — 차이는 모델이 아니라 그 주위에 세우는 구조에서 난다.

## 2. 7부작 지도

|----|------|-----------|--------|
| **Part 0** | 개요 & 세션 운용 | 진입점, 컨텍스트 규율 | (이 문서) |
| **Part 1** | 설계 인터뷰 & Decision DB | 실행 전 모호성 붕괴 | `design/decisions, assumptions, unresolved_questions` |
| **Part 2** | 문서화 & ADR | 의도를 복원 가능하게 | `docs/adrs, architecture, module_contracts, verification_plan` |
| **Part 3** | Bootstrap Agent | 1·2를 수행 + BUILD 게이트 | CLAUDE.md, 최소 슬래시 커맨드 |
| **Part 6** | Plan → Tasks → Implement | 검증된 설계를 단계적 구현 | `plan.md, tasks.md`, 구현 코드 |
| **Part 4** | Verification Agent | 구현이 설계와 맞는지 증명 | `verification/investigations, bugs, regressions` |

## 3. 세션 & 컨텍스트 운용 규율 (모든 단계 공통)

이 프로젝트가 반복해서 막혔던 직접 원인이 컨텍스트 관리 부재였다. 아래는 헤비유저들이 독립적으로 같은 결론에 도달한 규율이다.

### 3.1 60% 규칙
- 신선한 세션은 시작만으로 약 20k 토큰(시스템 프롬프트+도구정의+CLAUDE.md)을 쓴다.
- 품질은 컨텍스트 창의 **20~40%부터 저하**되기 시작한다(어텐션이 앞쪽 지시를 점점 덜 본다 = context drift).
- **컨텍스트가 용량의 60%를 넘지 않게 유지한다.** 넘기기 전에 3.2를 수행.

### 3.2 /compact보다 "덤프 후 /clear"
- 자동 컴팩션은 약 83.5%에서 발동하며 **손실이 크다(세부의 20~30%만 보존)**. 마이그레이션 결정 전체가 컴팩션에 지워져 작업을 잃은 사례가 보고된다.
- 권장: **현재 플랜과 진행 상황을 마크다운 파일로 덤프 → `/clear` → 그 파일을 읽혀 새로 시작.** 무엇을 남길지 사람이 통제하므로 손실이 없다.
- 이 매뉴얼에서는 그 덤프 대상이 곧 `design/`, `docs/`, `verification/`, `plan.md`, `logs/`다. 이미 파일로 존재하므로 `/clear` 후 그 파일들을 읽히면 복원된다.

### 3.3 컨텍스트 격리 (subagent / 병렬 탐색)
- 대량 출력을 내는 작업(검증 실험, 광범위 코드 탐색)은 **subagent로 격리**해 메인 세션을 더럽히지 않는다. 메인에는 요약(결론 + 파일 경로)만 돌려받는다.
- 단, subagent는 공짜가 아니다. **컨텍스트 격리가 실제로 필요할 때만** 쓴다(긴 작업 중 메인 청결 유지, 샌드박스 도구, 병렬 리서치). 단순 작업까지 격리하면 오히려 오버헤드다.

### 3.4 단순함 우선 (안티패턴 경계)
- **단순한 제어 루프가 다중 에이전트 시스템을 이긴다.** 복잡한 커스텀 커맨드를 길게 늘어놓는 건 안티패턴이다.
- harness(2026)가 이미 자동화하는 것(plan mode, 자동 컴팩션, Agent 병렬 탐색)을 커스텀으로 중복 구현하지 않는다.
- 커스텀 자산(슬래시 커맨드/스킬/subagent)은 **프로세스 규율을 강제하는 필수 최소**만 둔다. 권장: BUILD 게이트 1개부터 시작하고, 반복 고통이 실측된 것만 추가한다.

### 3.5 세션 시작/종료 체크리스트
**시작 시**
1. `logs/` 마지막 항목 + `docs/` + 현재 단계 산출물을 읽는다(=컨텍스트 복원).
2. 지금 어느 단계인지(인터뷰/문서화/구현/검증) 명시.

**종료/중단 시**
1. 진행 상황을 `logs/`에 append.
2. 열린 결정/질문을 `assumptions/` 또는 `unresolved_questions/`에 남긴다.
3. 다음 진입점(다음에 할 일 한 줄)을 로그 맨 끝에 적는다.

## 4. 도메인별 무게 조절

이 매뉴얼은 RTL/하드웨어 프로젝트에서 태어났다. 다른 도메인에 적용할 때 무게를 조절한다.

| 항목 | 하드웨어/RTL/펌웨어 | 일반 소프트웨어 |
|------|--------------------|----------------|
| Part 1 Constraints | **필수·엄격** (자원·타이밍·비트폭) | 가벼움 (성능 목표 정도) |
| Part 4 검증 | **8단계 + 골든 대조 필수** | 자기검토 라운드 + 테스트로 충분한 경우 多 |
| Part 5 Failure Pattern | 타이밍/순서/폭 패턴 카탈로그 | 도메인 맞게 교체 |
| 커스텀 자산 | 게이트·검증 격리 정도 | harness 기본기능으로 대부분 대체 |

**도메인 색깔(이번 SRCNN 등)은 각 문서의 `[사례 부록]`에만 둔다.** 본문은 도메인 중립이다. 주제를 바꾸면 부록만 교체하면 본문·프로세스·세션 규율은 그대로 재사용된다.

3. Part 1 인터뷰로 6영역을 채운다(자연어로 진행, 답을 즉시 DEC로 기록).

5. BUILD 게이트 통과 확인.
6. Part 6으로 plan→tasks→구현, 태스크마다 Part 4 검증.
7. Part 5로 산출물 연결 + 패턴 추출.
8. 세션 내내 Part 0 §3 규율(60% 룰, 덤프 후 clear) 유지.
