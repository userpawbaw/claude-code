# Part 1 — 설계 인터뷰와 Decision Database

> **이 문서의 위치**
> Claude Code 작업환경 7부작 중 1부. 코드를 한 줄이라도 생성하기 전에, 설계 의사결정을 구조적으로 수집하는 단계를 정의한다.
> 본문은 도메인 중립(어떤 HW/SW 프로젝트에도 적용)으로 쓰여 있고, 이번 SRCNN 프로젝트의 실제 사례는 문서 말미 **[사례 부록]** 에 격리한다. 주제가 바뀌면 부록만 교체하면 된다.

---

## 1. 목표

RTL(또는 임의의 구현물)을 생성하기 전에, 설계 의사결정을 **추측이 아니라 기록**으로 확정한다.

이 단계가 존재하는 이유는 단순하다. 구현 도중 발생하는 버그의 상당수는 코딩 실수가 아니라 **합의되지 않은 가정**에서 나온다. "이 신호의 valid는 몇 clk 지연인가", "패딩은 zero인가 replicate인가", "가중치는 어떤 순서로 메모리에 들어가는가" 같은 질문에 답이 정해지지 않은 채로 코드를 쓰면, 나중에 그 가정이 충돌할 때 원인 추적에만 며칠이 걸린다.

따라서 이 단계의 산출물은 코드가 아니라 **결정 기록(Decision Record)** 이다.

---

## 2. 핵심 원칙

1. **AI는 먼저 질문한다.** 요구사항이 모호하면 코드를 생성하지 않고 질문을 던진다.
2. **AI는 추측하지 않는다.** 정보가 없으면 "가정(assumption)"으로 명시적으로 분리하고, 사용자 확인을 받기 전까지 사실로 취급하지 않는다.
3. **모든 답변은 Decision Record가 된다.** 대화에서 확정된 사항은 휘발되지 않고 파일로 남는다.
4. **설계 완료 전 구현 생성 금지.** 아래 6영역이 모두 `Complete`가 되기 전에는 RTL Generation Mode로 넘어가지 않는다. (이 게이트는 Part 3에서 강제한다.)

> **업계 표준과의 정렬**
> 이 단계는 GitHub spec-kit의 `/constitution` + `/specify` + `/clarify`에 해당한다. spec-kit는 "협상 불가 원칙(constitution)"을 먼저 박고, 기능 명세를 만든 뒤, **구조화된 질문으로 모호성을 줄이는 clarify 단계**를 거친다. 우리의 6영역 인터뷰가 바로 이 clarify의 도메인 확장판이다.
> 핵심 통찰(헤비유저 공통): 결정당 정답률이 80%라도 결정이 20개면 전부 맞을 확률은 0.8²⁰ ≈ 1%다. 인터뷰는 이 20개의 모호한 결정을 *검토된 기록*으로 붕괴시켜 각각을 거의 100%로 끌어올린다. **좋은 결과의 차이는 프롬프트 품질이 아니라 실행 전에 세우는 구조에서 나온다.**

---

## 3. 수집 영역 (6 Domains)

인터뷰는 다음 6개 영역을 순서대로 채운다. 각 영역은 `Complete` / `Incomplete` 상태를 가진다.

### 3.1 Mission — 무엇을 만드는가
- 시스템의 한 줄 정의, 입력/출력 형태, 성공 기준.
- 예: "입력 H×W 영상 1채널을 받아 3레이어 conv로 1채널 출력을 만든다."

### 3.2 Constraints — 무엇에 묶여 있는가
- 타깃 디바이스, 자원 예산(LUT/BRAM/URAM/DSP), 클럭 목표, 정밀도(비트폭/고정소수점), 레이턴시/스루풋 요구.
- **이 영역이 가장 자주 누락된다.** 자원 예산이 없으면 "동작은 하지만 합성이 안 되는" 설계가 나온다.

### 3.3 Algorithm — 수학적으로 무엇을 계산하는가
- 연산 정의(커널 크기, stride, padding 규칙, 채널 흐름), 활성함수 유무, 수치 범위.
- 레퍼런스 모델(golden)을 만들 수 있을 만큼 구체적이어야 한다.

### 3.4 Dataflow — 데이터가 어떻게 흐르는가
- 메모리 계층(입력/중간/가중치 저장소), 레이어 간 데이터 이동, 병렬/직렬 구조, 버퍼링.
- 다이어그램 한 장으로 표현 가능해야 한다.

### 3.5 Implementation — 어떤 구조로 구현하는가
- 모듈 분할, 인터페이스(포트/valid 규약), 파이프라인 단수, 타이밍 정합 방식.
- 각 모듈의 입출력 계약(contract)이 여기서 정해진다 → Part 2의 `module_contracts.md`로 이어짐.

### 3.6 Verification — 어떻게 맞는지 증명하는가
- golden 생성 방법, 단계별 검증 순서, 비교 기준, 회귀 테스트 범위.
- "어떻게 검증할지 모르는 기능은 아직 설계가 안 된 것"으로 취급한다.

## 4. 산출물 디렉토리

인터뷰 결과는 다음 구조로 저장한다. (Claude Code에서는 리포지토리 루트 하위에 둔다.)

```
design/
├── decisions/            # 확정된 결정 (DEC-001.md, DEC-002.md, ...)
├── assumptions/          # 미확인 가정 (사용자 확인 전)
└── unresolved_questions/ # 답을 못 받은 열린 질문
```

세 디렉토리의 구분이 중요하다:
- **decisions/** — 확정. 코드가 의존해도 되는 사실.
- **assumptions/** — Claude가 진행을 위해 임시로 둔 가정. 빨간 깃발. 확인되면 decision으로 승격.
- **unresolved_questions/** — 아직 진행을 막고 있는 질문. 여기 항목이 있으면 해당 영역은 `Incomplete`.

### Decision Record 양식

```markdown
# DEC-007: 중간 feature map 저장 방식

- **Domain**: Dataflow
- **Status**: Confirmed (2026-06-01)
- **Decision**: 레이어 간 중간 결과는 URAM에 64bit word로 저장하고,
                다음 레이어 입력 시 FIFO로 16bit 단위 분해해 공급한다.
- **Why**: 입력 채널 병렬 처리를 위해 다채널 동시 read가 필요하고,
           URAM 폭(64bit)과 PE 입력 폭(16bit)이 달라 변환 단이 필요하다.
- **Affects**: uram_bank, fifo, line_buffer 입력 mux
- **Source**: 설계 인터뷰 2026-06-01 / 사용자 확인됨
```

## 5. 인터뷰 진행 규칙 (Claude Code 운용)

- **한 번에 한두 영역씩.** 6영역을 한 번에 다 물으면 답변 품질이 떨어진다.
- **객관식 우선.** 사용자가 모바일/짧은 답으로도 진행할 수 있게, 선택지가 있는 질문은 선택지 형태로 제시한다.
- **이미 알 수 있는 건 묻지 않는다.** 업로드된 코드/문서에서 추론 가능한 사실은 질문 대신 "확인" 형태로 제시한다. ("코드를 보니 padding=same zero인데, 맞나요?")
- **확정 즉시 기록.** 답을 받으면 그 턴에서 바로 decision 파일로 떨군다. 다음 턴으로 미루면 휘발된다.

## 6. 완료 게이트

6영역이 모두 `Complete`이고 `unresolved_questions/`가 비었을 때만 다음 단계로 진행한다.

이 게이트는 형식적 체크가 아니다. 실제로 이번 프로젝트에서 검증이 막혔던 지점들(아래 부록)은 전부 **이 단계에서 확정되지 않았던 가정**이 뒤늦게 터진 경우였다.

## [사례 부록] SRCNN_4_2_1 프로젝트에서 실제로 일어난 일

> 이 부록은 위 프로세스가 실제 프로젝트에서 어떻게 작동했는지(혹은 누락되어 문제가 됐는지)를 보여주는 살아있는 예시다. 다른 주제로 재사용할 때는 이 부록을 통째로 교체한다.

**프로젝트**: SRCNN_4_2_1 (1→4→2→1 채널, 3×3 conv, padding=same zero), 타깃 KV260(XCZU5EV).

**6영역이 실제로 어떻게 채워졌나 / 어디가 비었나:**

| 영역 | 상태 | 비고 |
|------|------|------|
| Mission | Complete | 150×150 1채널 → 3레이어 → 1채널 |
| Constraints | **뒤늦게 채워짐** | 초기엔 자원 예산 미확정. 단일 line_buffer 합성에서 **LUT ~10000** 확인 후에야 "병렬화 시 감당 불가"라는 제약이 드러남 → 동적 윈도우를 정적 윈도우+SRL32로 재설계 |
| Algorithm | 부분 Complete | conv 정의는 확정. **ReLU 유무가 미해결(PENDING)** — 현 RTL은 conv-only, 원형 SRCNN은 ReLU 있음. `srcnn_ref.py`는 `USE_RELU=False`로 맞춤 |
| Dataflow | Complete | 가중치 BRAM 32word 레이아웃, URAM 6뱅크, FIFO 64→16 변환까지 확정 |
| Implementation | Complete | 6모듈 분할(pe_group/weight_dispatch/channel_accumulator/uram_bank/FSM_pad/top), valid 파이프 3단 규약 |
| Verification | Complete | Python 사이클 모델 + golden 대조 절차 |

**교훈 1 — Constraints 누락의 대가.**
자원 예산을 초기에 decision으로 박지 않아서, 동적 인덱싱 line_buffer를 다 만든 뒤에야 LUT 폭증을 발견했다. 만약 "병렬 4채널까지 갈 것이고 채널당 LUT 예산은 X"가 DEC로 있었다면, 처음부터 정적 윈도우 구조를 택했을 것이다.

**교훈 2 — assumption을 decision으로 착각한 대가.**
"누적 결과가 15bit magnitude를 안 넘는다"는 건 한동안 가정이었다. 나중에 레퍼런스로 L2 raw 누적 max를 실제 계산(|1723| < 32767)해서야 decision으로 승격됐다. 이걸 확인 안 했으면 오버플로 정제 규칙 `{sign, [14:0]}`이 틀렸을 수 있었다.

**교훈 3 — PENDING은 명시적으로 남겨야 한다.**
ReLU 유무는 지금도 `unresolved_questions/`에 있어야 할 항목이다. 이걸 "일단 conv-only로" 하고 조용히 넘어가면, 나중에 설계 의도가 ReLU 포함이었을 때 전 레이어를 다시 검증해야 한다.
